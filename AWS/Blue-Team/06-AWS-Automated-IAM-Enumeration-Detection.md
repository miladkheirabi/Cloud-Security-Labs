# Automated IAM Enumeration Detection - AWS CloudTrail

## Challenge Overview

### Objective

Detect and investigate suspicious automated IAM enumeration activity within an AWS environment by analyzing AWS CloudTrail logs in an ELK-based SIEM.

The objective is to identify reconnaissance behavior where an attacker or automated tool attempts to enumerate IAM users, roles, permissions, and other identity-related information.

### Scenario

An enterprise AWS environment has AWS CloudTrail enabled and configured to record API activity across the AWS account.

As a security analyst, the task is to investigate CloudTrail events collected in the SIEM and identify suspicious automated IAM enumeration activity.

The investigation focuses on identifying patterns such as:

* IAM activity performed by IAM users
* Multiple failed API requests
* Repeated `AccessDenied` responses
* Activity generated by the Boto3 Python AWS SDK
* High-volume or automated reconnaissance behavior

The goal is to distinguish potentially malicious automated IAM reconnaissance from normal AWS activity.

### Skills Practiced

* AWS CloudTrail log analysis
* ELK / SIEM investigation
* AWS IAM monitoring
* Detection of reconnaissance activity
* User-agent analysis
* `AccessDenied` event analysis
* Behavioral correlation of CloudTrail events

AWS CloudTrail logs collected and indexed in an ELK-based SIEM.

## Investigation Process

### Initial Hypothesis

The challenge description indicates that suspicious activity is related to **automated IAM enumeration**.

An attacker performing reconnaissance may repeatedly call IAM APIs in an attempt to discover:

* IAM users
* IAM roles
* Policies
* Permissions
* Account identity information

Automated enumeration tools may generate a large number of API requests, including unsuccessful requests that result in `AccessDenied`.

A particularly useful indicator is the combination of:

* IAM user activity
* Multiple `AccessDenied` events
* Short time intervals
* Automated user agents such as Boto3

Expected indicators:

* AWS CloudTrail API activity
* `IAMUser` as the identity type
* Multiple `AccessDenied` events
* `Boto3` as the user agent
* Repeated IAM-related API calls
* Automated behavior occurring within a short period

---

## Investigation Workflow

The investigation was performed by gradually narrowing down the CloudTrail dataset and correlating multiple indicators of automated IAM enumeration.

### Step 1 - Identify CloudTrail Events

Query:

```
event.dataset: aws.cloudtrail
```

Purpose:

Filter the SIEM dataset to display events originating from AWS CloudTrail.

Why:

CloudTrail contains the API activity required to investigate AWS security events.

Starting with the CloudTrail dataset reduces the investigation scope and removes unrelated logs from consideration.

---

### Step 2 - Prioritize IAM User Activity

Query:

```
event.dataset: "aws.cloudtrail" and aws.cloudtrail.user_identity.type: "IAMUser"
```

Purpose:

Filter CloudTrail events to activity performed by IAM users.

Why:

The challenge focuses on suspicious activity performed through an IAM identity.

By narrowing the investigation to `IAMUser`, we can focus on activity associated with IAM credentials rather than other identity types such as assumed roles, AWS services, or federated identities.

This provides a more focused dataset for identifying suspicious user-driven activity.

---

### Step 3 - Identify AccessDenied Events

Query:

```
event.dataset: "aws.cloudtrail" and aws.cloudtrail.user_identity.type: "IAMUser" and aws.cloudtrail.error_code: "AccessDenied"
```

Purpose:

Filter the dataset to API requests that resulted in an `AccessDenied` error.

Why:

During IAM reconnaissance, an attacker may attempt to query APIs for which the compromised identity does not have permission.

Repeated authorization failures can therefore provide a useful indicator of enumeration activity.

A single `AccessDenied` event is not necessarily malicious. However, a large number of denied requests from the same identity or source within a short period can indicate automated reconnaissance or permission discovery.

Important investigation questions include:

* Which IAM user generated the events?
* How many `AccessDenied` events occurred?
* Were they generated within a short period?
* Which AWS APIs were being queried?
* Did the requests originate from the same source IP?
* Was the activity automated?

---

### Step 4 - Identify Boto3 Activity

Query:

```
event.dataset: "aws.cloudtrail" and aws.cloudtrail.user_identity.type: "IAMUser" and aws.cloudtrail.error_code: "AccessDenied" and user_agent.name: "Boto3"
```

Purpose:

Filter the suspicious `AccessDenied` events to requests generated using the Boto3 AWS SDK.

Why:

Boto3 is the AWS SDK for Python and is commonly used to automate AWS API interactions.

An attacker using an automated AWS enumeration script may therefore generate CloudTrail events containing a Boto3 user agent.

The combination of multiple indicators is more valuable than any individual indicator:

```
IAMUser
    +
AccessDenied
    +
Boto3
    +
Repeated API activity
    =
Potential Automated IAM Enumeration
```

This correlation provides stronger evidence of automated reconnaissance.

---

## Findings

The investigation identified CloudTrail activity consistent with automated IAM enumeration.

The relevant events shared several characteristics:

* The events originated from an IAM user.
* Multiple API requests resulted in `AccessDenied`.
* The requests were generated using the Boto3 user agent.
* The repeated authorization failures indicated attempts to access AWS APIs beyond the user's existing permissions.

The combination of these indicators is suspicious because it is consistent with an automated process attempting to discover the IAM permissions and identity structure of the AWS environment.

Important evidence:

```
event.dataset: "aws.cloudtrail"
aws.cloudtrail.user_identity.type: "IAMUser"
aws.cloudtrail.error_code: "AccessDenied"
user_agent.name: "Boto3"
```

The final filtered dataset represents the events most closely associated with the suspected automated IAM enumeration activity.

## Important Fields

| Field                                    | Description                                                                                                            |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `event.dataset`                          | Identifies the dataset from which the event originated. `aws.cloudtrail` indicates AWS CloudTrail data.                |
| `aws.cloudtrail.user_identity.type`      | Identifies the type of AWS identity responsible for the event, such as `IAMUser`.                                      |
| `aws.cloudtrail.error_code`              | Contains the AWS API error code. `AccessDenied` indicates that the request was denied due to insufficient permissions. |
| `user_agent.name`                        | Identifies the software or SDK associated with the API request. `Boto3` can indicate Python-based AWS automation.      |
| `event.action`                           | Identifies the AWS API operation that was performed.                                                                   |
| `source.ip`                              | Identifies the source IP address associated with the API request.                                                      |
| `aws.cloudtrail.user_identity.user_name` | Identifies the IAM user associated with the CloudTrail event when available.                                           |
| `@timestamp`                             | Timestamp associated with the event and useful for identifying bursts or repeated activity.                            |
| `aws.cloudtrail.event_source`            | Identifies the AWS service that received the API request.                                                              |
| `aws.cloudtrail.request_parameters`      | Contains parameters associated with the API request when recorded.                                                     |

## Detection Logic

The investigation can be summarized as a behavioral detection rather than relying on a single event.

A potentially suspicious pattern is:

```
IAM User
    |
    v
Multiple AWS API Requests
    |
    v
Repeated AccessDenied Responses
    |
    v
Boto3 / Automated User Agent
    |
    v
Short Time Window
    |
    v
Potential IAM Enumeration
```

The strongest signal comes from correlating these characteristics rather than treating every `AccessDenied` event as malicious.

---

## Findings Interpretation

### Why `AccessDenied` Matters

Attackers performing reconnaissance do not necessarily know which AWS APIs their credentials are allowed to access.

They may therefore query multiple IAM-related APIs and observe which requests succeed or fail.

This can generate a pattern of repeated authorization failures.

For example:

```
API Request 1 → AccessDenied
API Request 2 → AccessDenied
API Request 3 → AccessDenied
API Request 4 → AccessDenied
API Request 5 → AccessDenied
```

A burst of these events can indicate automated permission discovery.

### Why Boto3 Matters

Boto3 provides programmatic access to AWS APIs and is frequently used in automation scripts.

Therefore, Boto3 itself is **not malicious**.

However, when Boto3 activity is combined with:

* repeated IAM API calls,
* numerous `AccessDenied` responses,
* suspicious source IPs,
* and high request frequency,

it becomes a valuable behavioral indicator of automated reconnaissance.

## Defensive Recommendations

* Monitor CloudTrail for unusual IAM API activity.
* Alert on excessive `AccessDenied` events generated by a single identity.
* Correlate `AccessDenied` events with source IP, IAM identity, and user agent.
* Monitor bursts of IAM API requests occurring within short time windows.
* Investigate unusual Boto3 activity when combined with suspicious behavior.
* Establish baselines for normal IAM administrative activity.
* Apply least-privilege IAM policies.
* Avoid granting unnecessary permissions to IAM users.
* Prefer IAM roles and temporary credentials where appropriate.
* Enable CloudTrail across relevant AWS regions and accounts.
* Centralize CloudTrail logs in a protected logging environment.
* Use AWS-native detection capabilities such as GuardDuty and CloudTrail-based monitoring.
* Investigate suspicious credentials and rotate or revoke them when compromise is suspected.

---

## Key Takeaways

* AWS CloudTrail provides valuable visibility into AWS API activity.
* SIEM filtering allows analysts to progressively narrow a large CloudTrail dataset.
* `AccessDenied` events can provide useful reconnaissance indicators when they occur repeatedly.
* Boto3 is legitimate AWS automation software and should not be treated as malicious by itself.
* Combining multiple weak indicators can produce a much stronger detection signal.
* IAM enumeration is often an early-stage reconnaissance technique that can precede privilege escalation or unauthorized access.
* Investigations should focus on behavioral patterns rather than isolated events.
* Time, source IP, IAM identity, API action, error code, and user agent should be correlated during CloudTrail investigations.
